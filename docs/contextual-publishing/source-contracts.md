## Scoped normal-host AI composition

`NativeRuntimeDependencies.businessConfiguration` remains nil in normal composition. An accepted integration can supply `.publishingAIQuota`, `.publishingAITheme`, and independently `.publishingAIClub` exact POST routes through `BusinessRuntimeConfiguration`. These are not implied by `.publishingRead` or `.publishingWrite`. `AppSession.publishingAIDraftFactory` builds the real typed client; `makePublishingAuxiliaryService(feature:)` provides the club provider adapter. Both retain exact runtime context and durable opaque replay journals. An additional body guard rejects extra/missing fields, wrong method/path/origin/query, and unsupported modes. Role/market/session checks remain in the underlying service. No grant, credential, endpoint or provider is configured by these hooks.

## Topic pass and payment-return contract (later packet)

- Distinct `SelfPlayTopicID` / `TopicSelfPlayIntent`: JSON ownerType=1, ownerId, realName, phone, isUsePoint=0, payChannel=APP, stable requestId. Never activity ownerType=2, invented quoteSign, ticketId, or topicId wire aliases.
- Current signup notice metadata must come from a separately supplied deployment-specific provider. Record `activity_host_data_sharing / activity_signup / AGREE`, then read back matching server document version before create. The server owns docVersion; it is never submitted as a guessed field.
- Scoped runtime features independently cover topic+order reads, create, pay/app, consent read/write. Normal dependency configuration is nil. External-checkout storefront/product approval and device-payment approval are separate false-by-default flags. Digital-only unlocks must not be enabled through external checkout without an applicable Apple-policy decision.
- Immediately before create, re-read topic availability/closure/price. Durable opaque request/order marker precedes create; unknown response cannot create another intent. No name, phone, token or provider parameters are persisted. A payment-attempt marker precedes provider invocation and is monotonic across relaunch. Unknown payment cannot unlock another attempt.
- Every SDK outcome, including cancellation, goes through `OrderPaymentVerifier`. The result sheet is uncloseable during checking, holds authoritative accepted/paid results for two seconds, leaves failed result visible until close, and returns unknown/access-denied to a persistent host message. A server registration acceptance is distinguished from a paid verdict.
- Known unpaid orders can be explicitly reviewed and paid using the same registration ID, only when no prior provider attempt is unresolved. A fresh amount and notice are required. Unknown create/order states route to Orders/Ticket wallet. Automatic new-key rebuild on terminal 409/410 remains conservatively gated; this packet does not silently create a replacement order.
- The existing native WeChat bridge currently has an auth integration. The real payment SDK binding is a separate follow-on packet using verified official headers; this packet supplies the typed provider seam and does not claim an executable platform adapter by itself.

Apple compilation, synthetic XCTest execution, UI screenshot/runtime acceptance, actual backend contracts, verified current legal copy, approved storefront classification, registered merchant/app/universal-link settings and physical-device payment acceptance remain separate gates. No real requests or device effects were run while preparing this code.

The later native payment packet now supplies the concrete conditional WeChat payment bridge and scoped AppSession fallback. See `docs/wechat-payment-adapter/integration.md` and the pinned header evidence. The provider is code-bound, still unlinked/unconfigured and default-off; physical-device/provider acceptance is not complete. PayResp has no state or order ID, so the code uses one pending local order and mandatory authoritative server readback.

Recovery clarification: a known order can be re-read and its lock retired only after authoritative registrationStatus 3/4 with matching topic and registration IDs. The user then supplies a fresh review; no new order is sent automatically. Unknown create without an order ID stays locked because there is no verified lookup-by-requestId endpoint. A generic 409 is insufficient: the current backend also uses it for different-content, unprovable-legacy-fingerprint and existing-unpaid-pass conflicts. Pending consent writes are reconciled through the existing latest-consent API before any resend. Review-sheet cancellation never unlocks an in-flight create, and matched credential expiry detaches a pending provider wait.
