# Native merchant operations: bounded source migration

## Delivered surfaces

The merchant workbench now opens nine native destinations: store profile, storefront design, gallery, brand story, hosting settings, store character, voice/3D resources, city-location catalog and private interaction-template catalog. Catalog entries open location details or an owner-only template editor; a new template starts with no selected completion method. Forms provide validation, in-memory editing, dirty-state back/reload confirmation and immutable content review. Cards use the shared full-bleed image/scrim component without outlines; controls are native Form/List/Picker/TextField with semantic accessibility identifiers and image-only actions at least 44 points.

Normal production mutation composition remains off. MerchantOperationsService.save now has a dormant, scoped source-backed transport requiring explicit deployment/account/path approval, a fresh baseline, a session-check closure and durable pending storage. Without them it refuses dispatch; saveExample remains DEBUG-only. Example-save copy never claims real submission, approval, activation, publication or provider completion. Read routes remain subject to the app's existing approved-endpoint configuration; this integration supplies no endpoint, credential or deployment approval.

## Session, review and uncertainty behavior

`MerchantOperationsSession` binds account ID, epoch and in-memory token; the UI receives a credential-free random scope. Every document read rechecks access/me. Session/cancellation is checked after access before dispatching the document read, again after completion, and before unauthorized callbacks. Profile identity and owner-template ID must match the requested identity. Scope replacement hides drafts and confirmations; normal root integration keys operations navigation by scope. No token/PII logging or persistence is introduced.

Preparing review freezes a draft plus its baseline and scope. Editing cancels that confirmation. Confirmation is single-use and rereads the exact baseline before a DEBUG example mutation. A conflicting source requires reload with dirty-state confirmation. Explicit synthetic rejection retains text and draft; unknown example outcomes remain locked in the same coordinator even through refresh/leave/load and are never retried or declared failed from a readback. Synthetic locks remain in memory; the dormant approved reader restores minimal durable account/deployment/target locks. Partial story writes remain locked and are reported separately. Production activation still requires independent acceptance and a safe reconciliation design. See [operation adapters](operation-adapters-module.md).

## Remaining scope, deliberately not claimed complete

Merchant financial ledger/settlement/aftercare, CRM/customers, operators, recruitment, registrations, marketing/coupons/subscriptions, partner/relation/chapter management, city-node placement/claim workflows and node-level NPC/game authoring remain outside this batch. This batch adds store-level NPC configuration only; node-level NPC routes must never be substituted. Category/featured selectors, uploads, business-status switching, real saves, review/publication acceptance, media/voice/3D generation/consent/revocation, QR redemption and provider purchases are not operational. Merely constructing a request preview or fixture does not complete any business workflow.
