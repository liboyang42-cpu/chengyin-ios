# Club governance production assembly

The ordinary app now has an optional, typed `ClubGovernanceProductionFactory` route. It does not implement permissions by casting production HTTP as an offline transport. Default `NativeRuntimeDependencies.dormant` still grants nothing.

## Activation contract

A reviewed composition must supply `clubGovernanceApproval` with CN market, exact HTTPS API origin, account ID, regional storage namespace, nonempty reviewed policy version, exact read and mutation endpoint paths, and `ClubGovernanceActionGrant` values. Each grant is built from a validated command and binds one closed operation, its exact complete target scope (including activity ID), actual field target IDs, role/financial-kind choices, notification audience and matching risk; it does not retain free text or personal data. Financial, identity and provider actions must be selected explicitly; administrative permission cannot enable them. Notifications need their own selected operation and target. No wildcard path, all-target switch, remote flag, or UI role grants access.

The host builds the production service dynamically from current role/account/epoch/token/origin/market/namespace, attaches a retained coordinator, and supplies a metadata-only file journal. Every confirmation still fetches current access and target evidence, checks source permissions, target/version/member proofs, and verifies the reviewed snapshot. Dismissal/session/role changes are checked after persistence and at every subsequent await before write dispatch. Only the coordinator can mint the one-shot dispatch ticket after reservation; prepared reviews cannot bypass the journal through public access methods. The ticket carries cancellation/context validity to final transport entry. Transport checks exact authorization/method/URL/body and reuses its captured multipart bytes for chapter actions. Mixed offline/production composition remains strictly on the offline transport. An account-wide grant cannot confer event-scoped permissions.

Unknown or acknowledged attempts retain a durable target lock. An HTTP error, cancellation, malformed receipt or app restart cannot silently unlock or repeat an operation. The implementation intentionally supplies no guessed reconciliation endpoint or automatic retry. A cancellation after the journal reservation but before dispatch also remains conservatively locked.

## Source proof

Contracts remain the closed catalogs already verified against Flutter `club_ops_api.dart`, `club_crm_api.dart`, `club_compensation_api.dart`, `club_topic_ops_api.dart`, `club_api.dart`, `group_code_api.dart`, and `publisher_identity_api.dart`. The source checker verifies all 34 reads and 23 write paths. Current backend `ApiClubEventOpsController` still exposes series/create and update-future, occurrence cancellation and attendance correction; `ClubEventOpsServiceImpl` retains actor/club/activity access, optimistic version checks and cancellation wrap-up. No backend or Flutter source was copied into this implementation. Owner refund remains its separate existing adapter.

## Verification and remaining acceptance

Fifteen new non-DEBUG tests exercise the real production factory through a fake ordinary HTTP transport: default-off, exact grant/target/risk/namespace, durable-store requirement, request bytes and fresh access, revocation, role change, cancellation during reservation, cancellation during post-journal preflight, and durable unknown suppression, canonical target identity across navigation scopes and independent target locks. Tests also cover direct API bypass, field-target/audience widening, mixed composition and both multipart chapter actions. Existing permission/event-scope/version tests remain. Local parser and portable/source checks are not Swift execution. Apple compilation, runtime tests, backend deployment, legal/provider acceptance and real-device behavior remain separate gates. No real order, refund, notification or privileged action was sent.
