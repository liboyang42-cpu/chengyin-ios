# P034 image receipt recovery at the 200-block boundary

Independent review of insertion-gap tree `0191e2096551d1100fe42446dd3bf1cc0b14ef20` found a liveness defect: a valid 199-block draft could upload and save an inserted image as block 200, fail only its journal applied marker, then be unable to reopen the existing receipt. Fresh capture attempted to construct a new insertion first, which correctly rejected 200 blocks before receipt loading could occur. The image itself stayed saved; live marker retry was already available.

This repair retains the strict `blocks.count < 200` new-insertion guards verbatim. At exactly 200 blocks, capture may instead select one unambiguous durable, unapplied receipt for the requested chapter and exact append/insert-before action. Its target must recognize the exact existing postimage, including inserted image bytes, position, original draft, owner and bucket. No unrelated receipt, alternate anchor, 201-block draft, changed postimage or unstored-only receipt grants an opening.

The opening captures that exact journal entry and revalidates it on open. The existing flow receives an explicit receipt-only entry, forbids picking and uploading, and can apply only its already-existing exact postimage. It cannot use original-draft matching to create another block or switch to another receipt during load. Completion reuses the normal idempotent editor local-save boundary, then marks the same receipt applied. Existing lease, incarnation, topology, live content-ABA, typed-host and source-approval checks remain in force. A genuinely new 201st insertion is never enabled.

Per-block recovery uses the existing insertion menu. The end controls now apply capacity disabling individually: text and empty audio stay disabled at 200, while image can open only when capture found the exact recovery entry. Ordinary replacement of an existing image remains allowed at capacity and keeps its existing picker behavior.
