# Professional-topic local media foundation

This packet adds exactly six new paths on native commit `11800193a5f5057e6598b4e46e8ecb4a98e4572a`, tree `30cd0ace4249489a6ab22cc60f86a49edfb00bcf`. It supplies typed local selection, cancellation and metadata recovery for professional topics. It is not a completed image/video publishing feature. The ordinary static image paths and every existing source/test/configuration file remain unchanged.

`publishMode=pro` is the professional mode; product 1 and product 2 remain separate topic products. New selection requires an actual existing editor identity and FULL local edit context. The existing WHITELIST image behavior is untouched. This is a local constraint, not a server capability or proof that the caller may upload, own, moderate or publish content.

## Interfaces and stages

- `ProjectTopicMediaPolicy` requires injected limits for kinds, exact MIME types, count, aggregate/file bytes, dimensions/pixels, duration and mixing. There are no production business defaults. No policy means unavailable. Policy equality checks the entire value, so retaining an ID while changing its limits still retires an old preview.
- `ProjectTopicMediaContext` binds account, namespace, session/viewer/configuration revisions, valid draft UUID or topic ID, product, owner, professional mode, edit scope, monotonic draft revision and page visit. Namespace and draft identity use exact UTF-8 comparisons. The future caller must supply the real model's revisions, not a value derived from content equality.
- A picker may provide only `ProjectTopicMediaLocalReference`, an opaque local ID and revision. No path or URL is a media reference. `begin` issues a single active ticket; `prepareInspection` rejects empty, excessive and duplicate references before any inspection.
- `ProjectTopicMediaInspectionEvidence.inspect` invokes a separate inspector. Core streams and counts the complete bytes, computes SHA-256, checks the result's request/reference/digest, requires the corresponding image/video inspection assertions and validates all supplied local limits. All requests in a ticket share an aggregate budget. Failed or canceled budgets cannot be refunded or reused, including when an inspector mistakenly swallows a thrown consumer error.
- `finishInspection` accepts only evidence for the exact requests in the original order and creates an immutable preview. `confirm` consumes it once and returns a `LocalSelectionIntent`. Neither method edits `ProjectEditDraft`, saves storage, performs HTTP or writes legacy image fields. Cancel/back/withdrawal produce no intent. A reference-type owner avoids duplicated confirmation state through accidental value copies; its future UI controller must serialize state events. The chunk budget is independently locked.

## Inspection trust boundary

No production inspector is included. The interface is an integration seam, not an implementation of PhotosUI, file access, image decoding or video-track inspection. An injected inspector is trusted code and must independently be reviewed/tested. It must open only the exact owner-scoped regular app-managed file, bound reads before allocation, reject URL/symlink substitutions, inspect the same stable original bytes using real container/image/video APIs, and report their matching digest. File change, unreadable/corrupt format, missing video track, invalid duration, unsupported format or an interrupted read must throw. Picker-provided names, MIME declarations, dimensions or duration are insufficient.

Core can verify streamed byte counts and digest consistency; it cannot infer that an arbitrary injected implementation actually decoded an image or inspected a video track. A dishonest adapter could fabricate consistent reports. Production remains unavailable until the real adapter has executed these checks. The test inspector is explicitly synthetic and only proves the Core seam's intended behavior when those tests are run. No image or movie file was decoded by this packet's implementation or local checks.

## Metadata recovery

`ProjectTopicMediaLocalRecord` contains owner/draft binding and historical media facts only. It is Encodable but not publicly Decodable. Its sole decoder requires a caller-supplied record-byte ceiling before allocating JSON parser input, then rejects duplicate/escaped-alias keys through `ContentDraftJSON.parse`, then typed-decodes a private wire value and compares the full retained structure. Unknown schema or fields cannot be silently erased by an alternate public Codable path. The record contains no upload receipt, permission, review result or saved-success state.

Restoring verifies exact durable owner, deployment, draft identity, product and owner kind. A fresh session of the same owner may restore metadata, but the result is `needsReinspection`; file/hash/metadata must be checked again against a current policy before a new preview and intent. Missing policy stays unavailable. Changed file bytes or facts cannot reuse the old reference. This packet does not persist the files or record, establish cache lifetime, update an existing draft, or claim process cold-recovery of playable video. Those remain explicit App integration work.

## Validation and remaining work

There are 12 authored contract/inspection XCTest methods and 13 authored selection/recovery XCTest methods. They cover missing policy, injected boundaries, overflow, MIME/kind separation, nonce/reference/hash mismatch, sticky aggregate byte limits, raw-reference rejection, cancellation, one-use confirmation, account/draft/epoch/visit/revision ABA, policy withdrawal, strict local-record decode and mandatory reinspection. Swift execution, typechecking, Apple SDK/build, real files and UI behavior are NOT_RUN in this environment. Eight Python source-bound checks include 12 deliberately weakened-source negative controls; these are not Swift behavioral execution.

No UI methods or UI-budget changes are added. `Package.swift` discovers new Core and CoreTests paths without edits. The Xcode project is intentionally unchanged under the six-path scope; its two new Core source registrations need the central integrator's deterministic regeneration before App scaffold/build checks can pass. The packet's App-registration HOLD must not be reported as a runtime or full-delivery pass.

Next stages require the real native picker/inspector and local file/record store; the agreed topic-level upload/ownership/moderation/recovery and readback contract; and separately approved default-off composition. None is inferred from local format policy, opaque UUIDs, hashes, old image URLs or a successful local selection. Video never becomes valid by placing its URL into `imgUrl`/`imgArr`, and this packet does not alter story-node image/audio/album or the owned-topic JPEG cover producer.
