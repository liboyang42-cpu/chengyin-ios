# W02 encrypted durable journal candidate (inactive)

## Scope and activation

This adds an explicitly injected storage adapter to the independently reviewed W02 native client/coordinator. It does not add editor/UI wiring, routes, owner/deployment grants, authentication credentials, entitlements, or backend rights. The coordinator's default journal remains nil. `ContentDraftJournalFactory.make(scope:)` is an async, opt-in constructor with one fixed Keychain service and an OS-derived app-private storage location. No production composition invokes it.

The raw `ContentDraftService.mutate(ContentDraftMutation)` API has been removed. The service accepts only a `ContentDraftPreparedDispatch` whose constructor is fileprivate to the coordinator source. After persistence and exact-generation readback, the coordinator binds one immutable attempt to the full mutation, exact encoded body/path, scope/owner/key/version, session lease and live coordinator generation. Consumption is one-shot; retirement is a separate irreversible state, checked after every final journal suspension and again immediately before transport. Retries must return to the coordinator, rotate the journal generation and retain the original immutable mutation/key/version.

Network-capable transports additionally require the final `ContentDraftDurableJournal` to hold a sealed `ContentDraftSystemStorage` handle. Only the bounded fixed OS factory can mint this handle, even when App and Core compile in one module. The source moved from `App/ContentDraftSystemStorage.swift` to `Core/ContentDraftSystemStorage.swift`, guarded by Security/Darwin availability, with no new target and no storage-algorithm rewrite. Generic injected store conformance does not acquire the handle. A private immutable service transport is checked on every attempt; changing from a recorder to an arbitrary/network-capable executor cannot carry synthetic authorization across.

The internal final `ContentDraftRecordingTransport` has no network implementation, forwarding transport or executable callbacks. It only records requests and returns a configured synthetic response or suspends until explicitly resumed. It permits fake journals for in-process tests. Arbitrary `HTTPTransport` implementations, including other test recorders, receive the system-journal requirement. Protocol-only fake services remain synthetic test collaborators, not production dispatch authority. This boundary does not attempt to sandbox arbitrary same-process code that manually sends its own HTTP requests outside `ContentDraftService`.

The journal protocol now returns `ContentDraftJournalSnapshot`: a complete pending mutation plus a caller-held opaque generation. A coordinator retains its own snapshot through HTTP, and supplies that exact snapshot to replace/clear. An engine-global “last observed generation” is insufficient: two coordinators sharing one instance could otherwise let an old definitive rejection clear a newer uncertain attempt. The coordinator sets busy before every storage suspension and checks its irrevocable session/generation after each await. Initial, retry, and post-dispatch storage failures cannot authorize a fresh mutation.

This is source-level implementation and authored test coverage. Swift typechecking, Security/APFS execution, simulator/device behavior, performance and hardware power-loss proof are **NOT_RUN** here. It is not a production-readiness or release verdict.

## Endpoint size evidence and explicit local bounds

The reviewed private W02 controller, `ContentDraftCommand`, and `ContentDraftServiceImpl.canonicalPayload` contain no application-level maximum for `payloadJson`. The W02 migration declares a JSON column. The inspected 20 MB Spring setting is a multipart-request setting, not proof of the JSON save endpoint's limit. Deployed proxy, connector, database packet and runtime limits were not queried. **There is no verified hard endpoint maximum to report.** No private backend source was copied into this native packet.

The existing native seam independently limits each command/baseline payload to 524,288 UTF-8 bytes. The adapter preserves that bound and encodes the full immutable mutation, including its baseline, as a binary property list. It caps plaintext-plus-AES-GCM-combined overhead at 4,194,304 bytes. This leaves room for both maximum-size payload strings and binary-plist string encoding overhead. Key/device identity remains limited by the reviewed 64-UTF-16-unit checks. Scope components are each limited to 2,048 UTF-8 bytes; the full length-delimited binding is limited to 4,096 bytes. Each Keychain anchor is at most 8,192 bytes. Oversize/invalid values fail before HTTP; there is no oversized Keychain-blob fallback.

These are serialized-input caps, not a claim of constant peak heap usage. Foundation decoding, validated JSON structures and transient crypto buffers can require multiple bounded representations. Apple performance and peak-memory measurement at both payload limits remain acceptance gates.

## Confidential representation and exact scope

A length-delimited UTF-8 binding includes market, baseURL.absoluteString, realm/namespace, account ID, resolved owner ID, business type and client draft key. It deliberately excludes request role/scope, epoch and token. PERSONAL, CLUB and MERCHANT resolving to the same owner share one lock; the encrypted mutation retains its original request scope, and a coordinator opened under a different scope refuses to rebind it. Canonically equivalent but byte-distinct Unicode identifiers do not share a binding.

The fixed-service generic-password account attribute is the SHA-256 of that binding. The only changing Keychain metadata is a random 32-byte generation tag. Secret value data contains the binding, state, random blob name, encryption key and integrity digest. Private payloads, low-entropy payload digests and keys never enter attributes, filenames, logs or UserDefaults.

The complete mutation is encrypted with CryptoKit AES-256-GCM, a new random key per intent, a randomly generated nonce, and authenticated additional data binding the exact scope and blob name. Only ciphertext is written to a file. Keys reside solely in nonsynchronizing, data-protection Keychain secret data with `WhenUnlockedThisDeviceOnly`. Crypto/serialization, filesystem operations and Security calls run on non-main actors. No lock-state fallback, authentication prompt, access-group expansion or key migration is attempted.

## State machine, races and crash behavior

Every target has one permanent empty presence file and one small retained Keychain anchor. Presence filenames expose only the opaque slot digest and have no content. Retention is deliberate: deleting both evidence types on ordinary clear could make a missing device-only Keychain anchor after restoration look like a brand-new slot.

1. Fresh slot: read returns empty only if both anchor and presence marker are absent. Creation durably inserts the presence marker first, then uses `SecItemAdd` for the unique anchor. A crash between those steps leaves an unavailable lock, never a fresh slot.
2. Reserved intent: existing unresolved slots cannot be replaced. An explicitly empty anchor can become reserved only with a generation-conditional `SecItemUpdate`. A complete matching duplicate may be resumed; a different command fails. The reservation precedes immutable, exclusive blob creation.
3. Ready intent: a successful durable file write precedes reserved→ready CAS. Recovery reads only that named blob, with a 4 MiB cap, authenticates/decrypts it, validates the full mutation and republishes ready by CAS. Missing, partial, oversized, corrupt, inaccessible or unauthenticated blobs retain their reservation. No scan or automatic repair/erasure occurs.
4. Dispatch: false→true or exact true→true retry rotates generation by CAS and returns the new immutable snapshot. The coordinator and consuming service verify that exact snapshot before HTTP. A read rechecks the anchor after suspended presence/blob I/O, rather than returning a captured generation that another instance replaced during the read. A competing attempt advancing the generation before that verification fails before HTTP or prevents the older receipt/rejection from clearing it. Full pending value and caller generation are checked again inside clear.
5. Clear: only a matching caller snapshot can CAS ready→clearing. The committed clearing state permits deletion of that exact old blob. It then CASes to a new empty anchor with no encryption key, digest, blob name or pending payload. A crash during cleanup resumes the exact clearing state. The permanent presence marker stays. A stale cleaner cannot overwrite a newly reserved generation.

Only known matching receipts or a definitive rejection of an actual first attempt request clearing. Reads, logout, role changes and unknown outcomes never grant it. The safe API has no “forget pending” operation. Some interrupted first saves (for example, a presence marker without an anchor or a partial reserved file) require separately reviewed manual recovery; the adapter intentionally does not invent evidence that HTTP was never sent.

Recovery checks one slot and at most one blob; there is no directory scan or bulk deletion. Storage usage is bounded per target, not globally: one empty marker, one <=8 KiB anchor, and at most one <=4 MiB blob. Empty anchors/markers are retained per previously used target. A future host must manage the number of authoring targets and must not implement eviction of unknown locks. This packet supplies no retention/reset UI.

## Filesystem, backup and durability limits

The production root is a fixed `Library/Application Support/ContentDraftJournal-v1` tail under the OS-provided container/home. Only the trusted home prefix is canonicalized. Every tail/ancestor is descriptor-walked with `openat` and `O_NOFOLLOW`; directory creation uses `mkdirat` on the retained parent descriptor. No path-based metadata mutation, externally supplied factory root, alternate per-call service, global current-directory change or symlink traversal is used.

The journal directory is owner-only (0700); files are owner-only (0600), regular and singly linked. iOS creation establishes complete protection through the descriptor; reads verify that protection class, including for an existing directory. The local numeric class-A constant is sourced to Apple's File System Reference rather than assuming an SDK-exported macro. File writes are exclusive and never overwrite existing blobs. Each successful persistence path checks file/directory fsync and F_FULLFSYNC. Unsupported barriers, protection classes, permissions, short I/O and other errors fail closed. Actual APFS/simulator/SDK behavior is an Apple execution gate, not inferred from parsing.

Encrypted ciphertext and empty presence markers are eligible for normal OS backup. Restoring those markers without their device-only anchors blocks the affected targets. Missing markers with surviving anchors also block. The adapter does not recover keys on another device, promise migration, or treat a restore as permission to forget uncertainty. Simultaneous external deletion/rollback of **both** independent evidence stores, an older backup taken before the intent existed, malicious same-process access, device compromise and hardware that ignores flush requests are outside this local journal's proof. Such conditions require separate host/account recovery policy before activation.

## Official platform evidence

- [Apple AES.GCM seal](https://developer.apple.com/documentation/cryptokit/aes/gcm/seal(_:using:nonce:authenticating:)) and [open](https://developer.apple.com/documentation/cryptokit/aes/gcm/open(_:using:authenticating:)): authenticated encryption and additional-data validation; omitted seal nonces are generated randomly.
- [Keychain accessibility](https://developer.apple.com/documentation/security/restricting-keychain-item-accessibility) and [device-only unlocked items](https://developer.apple.com/documentation/security/ksecattraccessiblewhenunlockedthisdeviceonly): lock-state access and lack of cross-device migration.
- [Generic-password item class](https://developer.apple.com/documentation/security/ksecclassgenericpassword), [generic attribute](https://developer.apple.com/documentation/security/ksecattrgeneric), and [updating/deleting items](https://developer.apple.com/documentation/security/updating-and-deleting-keychain-items): unique insertion and attribute-based query semantics. Generation compare-and-swap is an implementation inference from those semantics; the actual old-tag query/new-tag update is explicitly covered by an authored simulator test and remains NOT_RUN.
- [Apple fsync manual](https://developer.apple.com/library/archive/documentation/System/Conceptual/ManPages_iPhoneOS/man2/fsync.2.html) and [fcntl manual](https://developer.apple.com/library/archive/documentation/System/Conceptual/ManPages_iPhoneOS/man2/fcntl.2.html): host flush versus full device-flush request. Neither guarantees all hardware survives arbitrary power loss.
- [Apple File System Reference](https://developer.apple.com/support/downloads/Apple-File-System-Reference.pdf), pp. 142–143: class A has value 1 and corresponds to complete protection. [Apple's fcntl header](https://github.com/apple-oss-distributions/xnu/blob/main/bsd/sys/fcntl.h) declares the protection-class and full-sync commands. Header inspection is not target-SDK compilation proof.

## Authored verification and remaining activation gates

Synthetic Core cases use only fake actor stores plus CryptoKit: competing insertions, full-value and stale-generation mismatches, shared/separate coordinator interleavings both before verification and during HTTP, interrupted marker/anchor/blob transitions, staged recovery, clear cleanup, lost anchors/markers, locked/corrupt storage, exact payload maximum and oversize, cross-account/deployment/owner/target/Unicode isolation, role aliases, and zero-HTTP rejection. Suspension tests cover logout/repeated taps during initial read, insert, replace, retry-read and clear.

Simulator-only AppUnit cases use a new synthetic Keychain service/slot per test and own-item cleanup, plus UUID-named temporary directories. They exercise real generation-CAS/deletion, exclusive bounded files, protection, permanent presence markers, symlink ancestors and weak existing directory permissions. They do not manipulate device lock state or claim physical-device privacy proof. No such test was run here.

Before enabling: independent source review of this exact packet; the compile-only API controls in `tools/check_content_draft_api_boundary.py` (after `swift test`, with `--module-path .build/debug/Modules`); exact integrated Swift/AppUnit builds/tests and unsigned CN/US simulator app builds on the approved Apple toolchain; measured large-record memory/latency; real crash/lock/unlock and protection-class acceptance; explicit, reviewed host ownership/session wiring and recovery/retention policy; and separately authorized endpoint/owner grants and editor schema integration. Existing earlier CI runs do not validate this delta.


## API compatibility and source-only verification

This is a deliberate source-breaking change for W02 writers. Direct callers must use `initialize` → `prepareSave`/`prepareDelete` → `confirm` and `retryExact` on a coordinator. `restore` and `list` remain journal-free, independently grant-gated service calls. Custom service doubles now receive the opaque prepared attempt and may inspect its immutable mutation; they cannot construct an attempt or a production storage handle. Every repository W02 caller has been migrated. Existing client, durability, suspension and simulator cases are retained; old callback-based response tests now use the sealed recorder's suspension controls.

New authored tests drive the real coordinator, encrypted journal engine and real service with synthetic actor stores and the sealed recorder. They cover exact persistence before HTTP, missing/locked/corrupt/partial stores, consumed/unstarted/in-flight-retired attempts, stale and cross-operation generations, full request mismatches, switching executor, late 401, revocation from the final grant-clock callback and generation advancement inside the final blob read across separate engines. Compile-only negative controls reject raw mutation calls and forged attempt/storage constructors, including from a testable same-module-equivalent context, and require a valid positive control first. Python checks and Tree-sitter parsing cannot establish that those Swift tests or access-control fixtures compile or execute; Apple execution remains NOT_RUN here.
