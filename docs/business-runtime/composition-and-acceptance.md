# Business runtime composition: bank, stamp, IM, publishing and verification

This packet repairs missing normal-host factories. It does not activate services, accept agreements, configure credentials or perform transactions. The shipped AppSession still receives `NativeRuntimeDependencies.dormant`; `businessConfiguration` and `bankDocument` default to nil.

## Installed composition

- Bank withdrawal: the wallet's normal destination constructs the existing real BankWithdrawalAdapter, metadata-only pending journal, exact-path transport and a fresh consent reader. The current document must come from a separately supplied trusted provider; latest server consent alone cannot establish the current version. Before both preflight and confirmation, the document and latest consent are read again and matched for bank_account_collection, withdrawal, AGREE, current version and unscoped ownership. No consent event is written
- Stamp: camera approval, source upload, source stamp creation, accepted output image origins and durable pending/retry ownership are independently supplied. The upload and create clients receive separate method/path subsets. Creation still requires the exact accepted uploaded image and reviewed user action
- IM: start/read/mute/send/upload receive individually configured exact paths. The writer is recreated for the account/role/epoch/token context; prior callbacks cannot reach a new identity. Image selection has its own per-IM approval closure and does not turn on the shared picker for merchant images. Existing message review, client message IDs and uncertain-result behavior are retained
- Publishing: publishing-mode reads and mutations receive separate approvals. Professional ProjectEditHTTPService is mounted with the actual selected personal/merchant owner, exact create/update/V2 paths, fresh preflight and existing secure pending store. Guest/unconfigured editing remains local. No player-activity identifier is converted into a topic-edit target
- Direct verification: a new production verification-only transport is separate from MerchantBusinessTestTransport. It cannot run general merchant/customer/staff/financial mutations and never labels the UI synthetic. Normal verification and city redemption retain current merchant permission checks, code-kind selection, second-step IDs and metadata-only unknown-result locks. Camera acceptance is separate from HTTP authority

Every business HTTP dispatch checks exact method/path, complete HTTPS base URL (including path), CN market, namespace, account, token, authentication epoch and role. Each feature rejects routes belonging to another feature. The source-backed client still validates its own payload, scope, result and review lifecycle. The default network implementation bounds response bytes and disallows redirects; tests can inject a fake transport.

## Required deployment inputs, without changing the defaults

1. Existing regional prerequisites remain unchanged: reviewed CN API origin/base path, namespace/realm, configured supported authentication and valid account. These business contracts do not opt a US build into a CN service
2. Provide a `BusinessRuntimeConfiguration` matching that exact account and deployment. Its `routes` dictionary contains only individually approved `BusinessRuntimeRoute(method:path:)` values. A read grant cannot grant a write, and a feature label cannot be repurposed for another endpoint. The full allowed catalog is implemented in `BusinessRuntimeFeature.accepts`; supplying an unlisted/wildcard route fails construction
3. Bank: POST api/compliance/consents/latest under bankConsentRead; POST api/fund/preflight/bank-withdrawal under bankPrepare; POST api/withdrawal/create under bankCreate. Confirm and reject are separately selected `bankChallengeActions`. Their exact api/fund/preflight/{id}/confirm or /reject routes exist only after a validated server preflight response supplies that positive challenge ID. Another challenge ID, omitted action or missing create approval is denied before the corresponding dispatch
4. Bank current-document blocker: the reviewed backend exposes agreement/get only for privacy and user_agreement. It does NOT expose the current bank_account_collection document/version there. A trusted `BankWithdrawalCurrentDocumentProviding` implementation must therefore be supplied from an independently verified current legal-document source for this deployment. It provides the version and official HTTPS document link. This packet deliberately leaves the provider nil and supplies no document text, version constant, guessed URL or consent-granting checkbox. Missing, stale, revoked or mismatched consent prevents financial-data submission
5. Stamp: stampUpload approves POST api/common/uploadOSS; stampCreate approves POST api/roam/stamp/create. `stampImageOrigins` approves only intended HTTPS returned-image origins. `stampCamera` and the installed NSCameraUsageDescription are separate; the existing screen obtains explicit purpose consent and OS authorization. Image upload and create remain explicit independent user actions
6. IM: imStart/read/mute/send approve their respective POST api/im/{start,read,mute,send}; imUpload approves POST api/common/uploadOSS. `imMediaOrigins` is a separate exact-origin set and `imImageSelection` separately permits the system image picker. Sending one message type does not activate location/microphone/camera providers or add unapproved endpoint paths
7. Publishing-mode reads: explicitly select needed POST api/publish/home, api/publisher/identity/status, api/category/list, api/user/list, api/template/my-list, api/project/my and api/ai/theme/draft/quota. Publishing writes separately select the applicable activity publish, topic create and project delete/status paths from the source catalog. The backend's publishing capability and ownership remain authoritative. Publisher identity registration and AI-assistance submission are not activated by these read or project-write grants
8. Professional editor: projectRead permits POST api/publish/home and/or api/topic/edit-detail. projectWrite separately permits only the reviewed subset of POST api/topic/create, api/topic/update, api/topic/v2/create and api/topic/v2/update. Existing V2 selection, immutable baselines, personal/merchant scope, review and pending-write recovery are preserved
9. Direct verification: independently select POST api/merchant/access/me and the needed groupcode/redeem, coupon/verification, registration scan_dynamic_code, scan_qr_code, scan_qr_code_chapter, scan_qr_code_station or citynode/redeem paths. A coupon-only grant cannot redeem a dynamic ticket. `verificationCamera` and OS permission are additional inputs, not derived from merchant role or HTTP access. An uncertain result retains the coarse durable redemption lock; viewing records cannot clear it

No configuration uses production URLs, account IDs, credentials, device samples or legal approvals in this repository. Actual backend, device, privacy, financial/legal and user acceptance must be verified separately before configuring a deployment.

## Source evidence and bounded exclusions

Contracts were derived from the existing native request adapters plus Flutter source a63e9e9 and current backend controllers for bank preflight/withdrawal, compliance, agreement documents, IM, merchant verification, project editing and stamp upload/create. No private implementation, production configuration or credentials are included.

The bank document source is a genuine external contract/configuration dependency, explicitly called out above. Owner refunds, pass/voucher/coupon presentation, live Roam, and the known player-edit cross-domain contract gap remain separate workstreams; this packet does not silently wire them to a guessed endpoint. Existing independent flags and legal/provider gates remain unchanged.

## Verification

Existing AppUnit default-dependency assertions now also check the new nil inputs. These tests make no real service/device requests. The packet's validation record distinguishes locally executed Python/source/parser checks from Swift/XCTest/Xcode checks that must run in Apple CI.
