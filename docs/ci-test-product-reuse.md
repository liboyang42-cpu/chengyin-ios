# Exact-commit XCTest product reuse

Run 49 (`54d18bc6c0406bda5dec88dd74c7fd09f1d63f6b`) passed Core tests, all unsigned builds, both profile checks, both test-bundle compilations and 14 app-hosted tests. Its UI jobs spent roughly 9–13 minutes in setup, compilation and test-runner startup before actual methods began. Several methods then failed accessibility/navigation assertions, and five early shards reached the 25-minute job limit. Those are separate failures; neither a compiled bundle nor a partial run is a UI pass.

The native job now packages its already compiled unsigned simulator `Products`, including both scheme-specific `.xctestrun` files. Runtime jobs download only the artifact from their current workflow run, verify the archive hash, exact commit and Apple toolchain, restore executable permissions via tar, and run `test-without-building`. Missing, ambiguous, nonportable or mismatched products fail; there is no silent rebuild fallback in CI. All app-unit methods and every discovered UI class remain selected exactly once across six shards.

Apple documents this build-for-testing / test-without-building workflow and the requirement to preserve bundle paths in [TN2339](https://developer.apple.com/library/archive/technotes/tn2339/_index.html). The official [download-artifact guidance](https://github.com/actions/download-artifact/tree/d3f86a106a0bac45b974a628896c90dbdf5c8093#limitations) recommends tar when permissions must survive transfer. The action is pinned to that inspected commit. No extra token or cross-run/repository artifact access is configured.

UI jobs have a bounded 35-minute ceiling. A 28-minute test-process deadline requests graceful interruption and allows time to finalize diagnostics; reaching it always fails with status 124, even if interruption returns zero. Tests are never omitted to meet the budget. If the result bundle is incomplete, the exporter labels a current-simulator diagnostic capture as incomplete rather than claiming a test attachment or visual pass.

Local coverage checks exercise modern/legacy xctestrun target discovery, portable paths, executable preservation, missing/duplicate targets, commit/toolchain mismatch, corrupt archives, path traversal rejection, exhaustive shard selection and timeout failure semantics. Run 51 on `be1f7436173224780b3022c7f8551a0d42bc68bb` verified the packaging/reuse path on Apple runners: all 23 app-hosted methods passed after restoration, and all six UI shards restored the exact products and executed. Its 345-method inventory reconciles to 271 passed, 66 failed, one interrupted and seven unstarted. One failed method timed out during Xcode app launch; the remaining failures require their recorded UI diagnoses. Shard 0 reached its bounded process deadline mid-run; shard 3 completed its 57 method bodies but reached the process deadline during finalization. Neither is a passed shard. Forty-one scenario PNGs and one explicitly incomplete simulator diagnostic were retained. Later UI repairs still require a fresh exact-commit run; no visual acceptance follows from source inspection alone.

The next workflow also retains text attachments from the explicitly synthetic UI fixtures, including accessibility hierarchy and assertion diagnostics. This is bounded one-day CI evidence, not real account data or a release artifact.


## Measured exhaustive grouping

Run55 exposed runtime imbalance after reuse was already working: one 58-method shard reached the 1,680-second runtime deadline with 48 passing methods and ten incomplete methods. Club operations consumed 425 seconds, template authoring 307 seconds before interruption, and activities 298 seconds. Three completed sibling shards consumed about 1,014–1,392 method seconds. Increasing the deadline is not needed to correct the count-only assignment.

The same six shards now use recorded per-method durations from runs54/55 as grouping costs. Discovery still reads every current XCTestCase and test method from source; the timing profile never selects, excludes or marks a test passed. New/unobserved methods receive an explicit 30-second estimate. Removed profile entries are ignored for selection. Invalid/missing timing input fails rather than silently changing strategy. Greedy longest-first assignment remains deterministic and covers each current class exactly once. The 28-minute process deadline, 35-minute job ceiling, exact-product verification and fail-on-incomplete behavior are unchanged. New Apple runtime evidence is required to validate the resulting balance.

## Independent build gates after the same product builder

Run55 test products were ready at 12:02:08 UTC, followed by 497 seconds of sequential device and US builds before runtime jobs could start. Observed effective Mac concurrency was five. The next graph lets app-hosted tests and all six UI shards depend only on the verified product builder, while unsigned device and US builds run as independent required jobs. Every consumer verifies the exact checked-out SHA and Apple toolchain; product restoration still verifies its archive/hash/manifest. No cross-SDK binary reuse or unverified cache is introduced.

The legacy check display name `native` now belongs to the fail-closed final aggregate; the builder is displayed as `native-products`. The aggregate requires all build/profile/link, secret, app-hosted and UI jobs to succeed, matching build fingerprints, and six uniquely named successful UI-shard completion outputs. Missing, skipped, cancelled, stale or partial work cannot satisfy it. Branch-protection settings are unchanged. This uses GitHub's documented [job dependencies](https://docs.github.com/en/actions/how-tos/write-workflows/choose-what-workflows-do/use-jobs) and [job outputs](https://docs.github.com/en/actions/how-tos/write-workflows/choose-what-workflows-do/pass-job-outputs).
