## Audit of the existing native code against the contract

- **Update keeps omitted fields (BK-AUTHOR).** `ProjectEditContract.payload` already sends the exact edit-detail readback values for `publishMode`, `teamMode`/`teamMaxMembers`, `xpBudget`, `selfPlay`, `selfPlayPrice`, `selfPlayQuota` (`topicCarryOver`). Native therefore never relies on the server to fill gaps, and it never sends a guessed default. An explicit 0 is sent as 0. `ProjectTeamConfiguration.canSubmit` blocks team values outside 0...2 / 2...4, which covers fixture teamMode=7. `ProjectTopicBudgetCarryOver` keeps create bodies without `xpBudget`.
- **Full replacement.** Chapters, tickets and collaboratorIds are always sent as whole arrays, never as a generic PATCH.
- **Re-read after save.** After an acknowledged update, `ProjectEditCoordinator.continueAcknowledged` re-reads `/api/topic/edit-detail` before the next edit, so the next baseline uses the rebuilt chapter IDs, node IDs and `configVersion`. Each submit preflight also checks that a fresh read equals the bound baseline (`revisionConflict` otherwise).
- **Lost response.** On the first create, the durable `dispatchStarted` lock keeps the outcome UNKNOWN. `terminalReceipt` returns nil because no reconciliation contract exists, and nothing is matched by name.
- **Failed publish keeps edits.** The local draft envelope is written before submit. A rejected result clears only the pending intent.
- **Media recovery.** Per-draft journals already keep three states apart: `ProjectStoryImageJournal`, `ProjectNodeImageJournal` and `ProjectStoryAudioJournal`. An entry with no receipt means the upload outcome is unknown and is never retried automatically. An entry with a receipt that is not applied means the server reference is confirmed but not yet in the draft. An applied entry means the confirmed reference is in the draft. A local selection that has not started is never persisted. Existing tests already cover these, including close during upload and a received-but-unstored receipt (`ProjectStoryImageTests`, `ProjectNodeImageTests`, `ProjectStoryAudioFlowTests`). No new abstraction was added.
- **Template authoring** (`TemplateAuthoringService`/`SavedDraft`/`PublishReceipt`/`MediaReferenceSnapshot`) uses `/api/template/*`, not the BK-AUTHOR topic routes. It already binds the saved and published IDs to the exact request hash and owner, and it keeps unknown outcomes as `uncertain`. It is unchanged.
- **Ending reads (BK-NARRATIVE).** `JourneyEndingDocument` keeps `chapter` as the raw authoritative object or null, and `JourneyNarrativeView` renders the chapter only when it is an object. Otherwise it shows the title and summary. Native never rebuilds an ending from current chapters.

## Gap fixed

The frozen A03 contract says a present `ending.fallback` must be a JSON boolean; a string, number or null is rejected on v2 writes. Native had two problems:

1. `ProjectEditStoryContract.validatePayload` accepted `fallback: null`. It is now rejected locally, before the durable dispatch marker.
2. `ProjectEditRichStoryContract.attachEndings` copied any raw legacy `journeyStory` ending `fallback` into a chapter ending. It now keeps only `true`/`false`, which matches the mini program's `fallback === true` reading in `story-ending.js`. A non-boolean value was never a fallback in the mini program, and the absent key keeps that meaning.
