# Registration coordinator: in-memory domain slice

Reviewed 2026-10-01 against the retained Flutter checkout. This slice adds no UI wiring, endpoint configuration, payment SDK, consent submission, polling, storage, live request, cancellation/refund operation or order-success verdict.

## Source evidence and deliberate boundary

- `lib/data/api/activity_api.dart`, `quote` and `createRegistration`: quote binds activity/ticket/points selection; create sends the signed quote and a caller-retained `requestId`. The source explicitly warns that allocating a new ID on repeated submission can create duplicate tickets. Existing Swift JSON/service contracts preserve these fields.
- `lib/feature/activity/activity_detail_page.dart`, `_SignupSheetState._refreshQuote`, `_submit`, `_attemptCheckout`: user confirmation, current participant values, quote prerequisites and retained request ID; the consent record is submitted separately before creation. The native coordinator's caller must complete that separately verified consent flow before invoking `confirm`. This coordinator does not claim consent exists and is not ready for live UI checkout.
- The same source's `_cancelPendingOrder` only clears an ID after cancellation succeeds. A local dismissal, cancelled Swift task, network timeout or account change provides no such server evidence. This implementation deliberately has no reset or create replay API.
- `_attemptCheckout` currently presets success when payment parameters are absent. Create result variants include idempotent replay; absence of parameters and a zero total therefore do not establish a new payment or completed registration. The native state says only `responseReceived`.
- `lib/feature/orders/payment_verifier.dart`, `classifyRegistrationStatus`, checks payment/registration value 2 before failure-looking values 3/4. Its polling timeout/abort produces unknown. `test/feature/orders/payment_verifier_test.dart` tests individual success, failure and pending cases but does not settle conflicting-field precedence against authoritative server rules. This slice retains raw numeric/null statuses, including conflicting combinations, rather than porting a success/failure classifier. No timers or polling are ported.
- `RegistrationService.readStatus` already enforces `/api/registration/info` identity. The coordinator independently rejects an injected snapshot whose ID differs from its known create response.

## State and operation rules

`RegistrationCoordinatingService` is an injected main-actor protocol, also adopted by the existing `RegistrationService`. The coordinator creates no transport and has no default service. A synthetic manually completed implementation drives the tests.

1. `setAccount(id:token:)` requires a positive verified account ID and a valid token. It advances the account generation every time, even when reauthenticating the same account. The caller must provide the verified identity belonging to that credential. `clearAccount()` also advances the generation, clears the active credential and removes the old account's visible state.
2. `select` accepts a selection only before an intent is submitted. Any actual activity/ticket/points change invalidates the quote, including changing away and back. A quote is never accepted as a caller-supplied confirmation parameter.
3. `requestQuote` is explicit and invalidates a previous quote immediately. Completion is bound to both the captured account generation and quote/selection generation. A stale response or error cannot replace a newer quote, expose another account's data, or sign out a newer session. Incomplete quotes remain visible as raw data but cannot enable confirmation.
4. `confirm` is explicit. It validates participant fields, constructs one immutable intent, and installs its lock before awaiting the service. Duplicate confirmations, changed selections and re-quotes are blocked once that record exists. Participant values, original signed quote and request ID remain exactly those of the first accepted confirmation. No create call occurs merely because a quote becomes usable.
5. Every create error after invoking the boundary is conservatively represented as `outcomeUnknown`, preserving structured business/HTTP diagnostics where available. No unverified status code such as 409 or 410 authorizes retry, quote refresh, key rotation or replacement. This is an uncertainty policy, not a statement that a business rejection necessarily created an order.
6. Task cancellation after invocation and `cancelPendingOperations()` retain the submitted intent. The latter invalidates local completion handling, without claiming to cancel an already-dispatched server operation. Late completions following explicit local cancellation are ignored. Cancellation before invocation sends nothing and does not install an intent.
7. `readKnownStatus()` sends exactly one explicit read for the ID returned by this account's create response. It deduplicates an in-flight read. Failures retain the known intent; another explicit read is allowed. The snapshot is raw evidence only: neither it nor any create response unlocks another create. There is no arbitrary-ID adoption, ID guessing or lookup-by-request-ID contract for an unknown create response.

The action return value distinguishes applied state transitions, ignored stale completions, and blocked operations. `applied` does not mean order/payment success; inspect the typed state. A failed read or quote changes only its own state. Arbitrary error descriptions are discarded instead of retaining potentially credential-bearing URLs or diagnostic text; supplied server codes/messages stay available in structured errors.

## Account isolation and retention limits

This is one flow with at most one submitted intent per account for the lifetime of its coordinator. Records for inactive accounts remain private in memory; only the current account's intent/creation state is exposed. Changing accounts during creation conservatively locks the old account's intent as unknown. Returning to that account restores the same selection, full intent and lock, without restoring its credential, quote or readback. The old generation's completion cannot change the restored record. A different account may operate its own independent intent with its own captured credential.

The in-memory record includes participant data and an opaque quote/offer token needed to preserve the full intent. There is no logging, UserDefaults/Keychain/file write, encoding for storage or persistence adapter in this slice. Keep the coordinator alive across sheet dismissal and account transitions; replacing it is not recovery. Deallocation, a process restart or a new coordinator loses the lock and cannot guarantee idempotency. There is deliberately no restore API because restoring a request ID without the exact intent and verified account would be unsafe.

Before live integration, establish protected account-scoped durable retention/restoration, consent-recording integration, a supported recovery path for unknown registration IDs, authoritative terminal-status precedence, and the policy for ending an old intent and beginning a genuinely new registration. None is supplied here. In particular, do not present a fresh coordinator after a crash as evidence that a prior order failed or that another order is safe. There is also no local quote TTL inference: only the server can validate its opaque signature.
